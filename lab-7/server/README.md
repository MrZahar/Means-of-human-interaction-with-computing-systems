# Лабораторная работа № 6 — Express: HTTP-сервисы и форматы данных

**Предметная область:** The Superhero Box, управление пользователями и заказами из лабораторной работы № 4.

## 1. Запуск

Требуется **Node.js 18+**. В отличие от ЛР5 здесь устанавливаются зависимости: `express` (HTTP-сервер) и **`fast-xml-parser` — исключительно для генерации XML**.

```bash
npm install
npm start
```

Открыть **http://localhost:3000/page**. Для запуска с перезагрузкой при изменении JavaScript: `npm run dev`. Для автоматических проверок: `npm test`. Порт можно изменить через `PORT=4000` (в PowerShell: `$env:PORT=4000; npm start`).

**Важно:** данные действительно изменяются в `data/users.json` и `data/orders.json`. Для сброса состояния восстановите эти файлы из ZIP. Не изменяйте файлы одновременно с отправкой запросов записи. Сервер читает JSON **при каждом HTTP-запросе** и видит изменения на диске без перезапуска.

## 3. Описание каждого HTTP-сервиса

| Метод и адрес | Что делает | Входные данные | Результат |
|---|---|---|---|
| `GET /page` | Возвращает страницу с фронтендом | Нет | HTML с подключёнными CSS/JS |
| `GET /` | Аналогичная главная страница | Нет | HTML |
| `GET /api/users` | Возвращает пользователей | Нет | JSON-массив |
| `GET /api/orders` | Возвращает заказы | Нет | JSON-массив |
| `GET /api/users/:id` | Возвращает одного пользователя | ID в URL | JSON-объект или 404 |
| `GET /api/orders/:id` | Возвращает один заказ | ID в URL | JSON-объект или 404 |
| `POST /api/statistics` | Принимает параметры фильтра, **не изменяет данные**, возвращает JSON | `{ "role": "all", "status": "all" }` | `{usersCount, ordersCount, revenue, role, status}` |
| `POST /api/users` | Принимает пользователя, проверяет, сохраняет | `{name,email,phone,role}` | JSON созданного пользователя, статус 201 |
| `POST /api/orders` | Принимает заказ, проверяет, сохраняет | `{userId,product,quantity,price,status}` | JSON созданного заказа, статус 201 |
| `PUT /api/users/:id` | Изменяет пользователя | ID и поля в JSON | Обновлённый JSON |
| `PUT /api/orders/:id` | Изменяет заказ | ID и поля в JSON | Обновлённый JSON |
| `DELETE /api/users/:id` | Удаляет пользователя без заказов | ID в URL | `{ "deletedId": id }` или 409 |
| `DELETE /api/orders/:id` | Удаляет заказ | ID в URL | `{ "deletedId": id }` |
| `GET /api/export/users` | Экспортирует пользователей | HTTP-заголовок `Accept` | Файл JSON, HTML или XML |
| `GET /api/export/orders` | Экспортирует заказы | HTTP-заголовок `Accept` | Файл JSON, HTML или XML |

**Два разных POST-сервиса:** `/api/statistics` принимает фильтры и только возвращает JSON-статистику, а `/api/users` и `/api/orders` принимают данные для их сохранения. Это демонстрирует оба типа POST-операций, требуемые в задании.

### Примеры запросов (PowerShell)

```powershell
# JSON через GET
Invoke-RestMethod http://localhost:3000/api/users

# POST возвращает статистику без изменения файлов
Invoke-RestMethod -Uri http://localhost:3000/api/statistics -Method Post -ContentType 'application/json' -Body '{"role":"all","status":"all"}'

# POST создаёт нового пользователя
Invoke-RestMethod -Uri http://localhost:3000/api/users -Method Post -ContentType 'application/json' -Body '{"name":"Новый клиент","email":"new@example.com","phone":"+375291234567","role":"customer"}'

# Для экспорта с Accept проще использовать curl.exe (не псевдоним PowerShell curl)
curl.exe -H "Accept: application/xml" -o users.xml http://localhost:3000/api/export/users
curl.exe -H "Accept: text/html" -o users.html http://localhost:3000/api/export/users
curl.exe -H "Accept: application/json" -o users.json http://localhost:3000/api/export/users
```

## 4. Создание форматов: ограничение по библиотекам

В соответствии с дополнительным требованием **пакет используется только для XML**:

- **XML**: `XMLBuilder` из пакета `fast-xml-parser` в функции `packageXml()` (`src/serializers.js`). Заголовок: `application/xml`.
- **HTML**: собственная функция `manualHtml()` строит строки документа, таблицы и ячейки, экранирует специальные символы. Заголовок: `text/html`.
- **JSON**: собственная рекурсивная функция `manualJson()` формирует JSON и экранирует строки. Заголовок: `application/json`. Файлы источника читаются стандартным `JSON.parse`; штатный `JSON.stringify` используется для записи JSON-хранилища и тела HTTP-запроса, **не** для построения скачиваемого JSON.

Экспортный сервис вызывает `chooseFormat(req.headers.accept)`, затем `serializeExport(type, records, format)`. HTTP-ответ выставляет `Content-Type`, `Content-Disposition: attachment` и `Vary: Accept`. Неподдерживаемый формат даёт **406 Not Acceptable**. Кнопки на странице выставляют заголовок `Accept`, создают ссылку на полученный `Blob` и скачивают файл.

## 5. Как фронтенд обменивается данными с сервером

1. Браузер запрашивает `GET /page`: Express отдаёт `public/index.html`; HTML подключает `app.js` и `style.css`.
2. При загрузке JS выполняет `fetch('/api/users')`, `fetch('/api/orders')` и `POST /api/statistics`. Ответы JSON преобразуются в объекты и отображаются в таблицах. При этом ячейки создаются через `document.createElement()` и `textContent`, а не опасную HTML-вставку.
3. При сохранении формы вызывается `fetch()` с `POST` или `PUT`, телом JSON и заголовком `Content-Type: application/json`.
4. После успешной операции заново запрашиваются оба списка, поэтому интерфейс показывает актуальные серверные данные. При удалении используется метод `DELETE`.
5. Для скачивания файлов `fetch('/api/export/...', {headers:{Accept:'...'}})` получает `Blob`.

## 6. Ошибки, валидация и JSON при работе сервера

- **400** — некорректные поля формы, неверный ID, некорректное JSON-тело запроса, недопустимая роль или статус.
- **404** — несуществующая запись, маршрут или тип данных.
- **409** — email уже существует либо пользователь связан с заказами.
- **406** — неподдерживаемый `Accept`.
- **413** — слишком большой JSON-запрос (32 КБ).
- **500** — повреждён JSON-файл данных.
- **503** — JSON-файл недоступен либо запись в файл не удалась.

Данные хранятся в двух отдельных JSON-файлах. `readCollection()` выполняет `fs.readFile()` при каждом запросе, поэтому изменения внешним редактором подхватываются без перезапуска. `writeCollection()` сначала записывает временный файл, затем переименовывает его в целевой (уменьшая риск частичной записи). `transaction()` выполняет запросы изменения последовательно, не позволяя двум изменениям перезаписать друг друга в рамках одного процесса Node.js.

**Отрицательные сценарии для защиты:** отправьте пустое имя; некорректный email; email-дубликат; заказ на несуществующего пользователя; удаление пользователя, у которого есть заказ; запрос с `Accept: image/png`; GET несуществующего ID. Для проверки повреждённого JSON замените на время содержимое `data/users.json` строкой `[broken`, выполните GET и восстановите файл. Сервер при этом не завершается.

## 7. Краткий сценарий защиты

1. `npm start`, открыть `http://localhost:3000/page` и показать две таблицы.
2. Нажать «Сохранить» в форме пользователя, открыть `data/users.json`: в нём появилась запись; затем отредактировать или удалить её.
3. Создать заказ, показать связь `userId` и автоматическое обновление статистики через POST.
4. Нажать три кнопки экспорта; открыть XML, HTML и JSON. Продемонстрировать `src/serializers.js`.
5. Не завершая сервер, вручную поменять одно имя в `data/users.json`, нажать «Обновить данные»; новое значение отображается.
6. Отправить некорректные данные и показать сообщение с корректным HTTP-статусом.

**Создание GitHub-репозитория и коммитов** выполняется самостоятельно — их нельзя создать внутри ZIP-файла без доступа к вашему GitHub.
